# V1 consumer safety hardening — independent security and privacy review

**Owner:** Security / Privacy reviewer  
**Scope:** Installer target and purge safety, disposable test roots, isolated App/update lab paths, DevelopmentTest trust boundary, release-script deletion paths  
**Authority:** PRD §§24, 25.1–25.2 and AC-S03; `docs/handoffs/V1-CONS-SAFETY-002.md`; ADR-014/015  
**Decision:** CHANGES REQUESTED. No Gate E2 or consumer-closure decision is made here.

## Evidence and method

Read `PROJECT_BOARD.md`, `IMPLEMENTATION_STATUS.md`, the PRD sections, the safety and update-drill handoffs, and current source for `InstallerEngine`, `TestSandboxGuard`, `TestDeleteGuard`, App startup/session wiring, `UpdateService`, the dedicated fixtures, and release/package scripts. This is read-only source review. No destructive fixture, installer, uninstaller, global runner, or release drill was run. The shared tree has concurrent changes; line references describe the inspected working tree and should be refreshed after final integration.

## Actionable findings

1. **Resolved in source, rerun pending — release drill path and cleanup.** During review, `scripts/release.ps1:125–182` changed to use a sentinelled `%TEMP%\SpeedMeterPro.Tests\<GUID-N>` root with an `install` child and `Remove-TestSandboxRoot` cleanup. `scripts/test-sandbox.ps1:1–40` verifies the absolute GUID parent, sentinel and reparse entries before deletion. This now matches the dedicated installer leaf contract. No release drill was run during this review; the validation and recursive delete still have a local filesystem race if another process mutates the tree between checks and removal.
2. **Resolved in source, packaging check pending — generated legacy uninstaller.** During review, `scripts/package.ps1` removed the generator for `Install.ps1` and `Uninstall.ps1`; ZIPs are now labeled diagnostic payloads, with the signed Setup.exe as the supported install/uninstall path (`package.ps1:52–53`). Inspect the next produced ZIPs to confirm no stale scripts remain. Existing extracted ZIPs from earlier runs must not be treated as the new output.
3. **P2 — Deferred production batch has a validation-to-execution gap.** `InstallerEngine.ValidateUninstallRequest` validates the target and tree before shutdown and data operations (around `461–490`), then later writes a batch to delete the target after process exit (around `439–455`). The path can change in the intervening interval; the batch does not revalidate the marker, target, or reparse boundary. The handoff acknowledges this race. `RejectCmdCharacters` also checks the entire default path: a legitimate profile or temp path containing a CMD metacharacter makes normal per-user setup/uninstall fail. Replace the batch with a managed helper that validates immediately before deletion; until then, document and test the native behavior. The same temporal gap applies to a mutable purge tree between `RejectReparseTree` and recursive `Directory.Delete`.
4. **P2 — Package-output recursive deletes remain outside the shared guard.** `scripts/package.ps1:23–24,73–75,95–96` removes release and setup-publish trees without a reparse-boundary check. The update fixture now creates and deletes its temp root through `TestDeleteGuard` (`ConsumerUpdateFixtures.cs:300,386`), and the release drill uses `scripts/test-sandbox.ps1`. Review the package-output paths and any remaining direct recursive deletes in the final tree before the package script executes. Lexical containment of a versioned path is weaker than a checked reparse boundary.
5. **P2 — Canonical shutdown still enumerates unrelated lab processes.** Noncanonical targets now match the exact executable path, but canonical install/uninstall still call `GetActiveInstancesForTarget(target, false)` and the older name/title-based `RequestGracefulShutdown` (`InstallerEngine.cs:172–180,385–392`). A concurrent isolated lab app has the same process name and window title; the canonical path can send `WM_CLOSE` to it or wait for it to exit, causing an unrelated interruption or abort. Match canonical processes by their installed executable path as well, then signal the SID event and matched HWNDs only.

## Source changes accepted on inspection

- `UninstallOptions` no longer exposes an arbitrary user-data path publicly. Its internal test override must be a child of the same sentinelled disposable root as the install target (`InstallerEngine.cs:34–44,538–550` at initial review; later line shifts possible). Real purge resolves to the current user's canonical data root. The test fixtures inject isolated user data and reject a real-data override.
- `TestSandboxGuard` requires an absolute GUID root directly under `%TEMP%\SpeedMeterPro.Tests`, validates a matching sentinel, rejects dot segments, and checks existing reparse components and deletion trees (`TestSandboxGuard.cs:18–104`). `TestDeleteGuard` validates the root and child entries before recursive deletion (`TestDeleteGuard.cs:10–26`). These checks address the prior fixture's accidental selection of real `%LocalAppData%\SpeedMeterPro`; they do not make the recursive delete race-free under concurrent filesystem mutation.
- Fresh installs reject a nonempty unrecognized target, while uninstall requires a marker bound to the exact path and both binaries or a legacy canonical install (`InstallerEngine.cs:492–509`). The current dedicated product-leaf requirement rejects drive roots and broad directories. Command expansion/metacharacters are rejected before the legacy batch is generated (`511–535`).
- During this review, noncanonical install/uninstall shutdown was changed to match the executable path and post `WM_CLOSE` only to matching processes (`InstallerEngine.cs:172–185,382–397,578–623`). Earlier source could signal the unrelated real app during a sandbox/custom operation. The change is accepted on source inspection; finding 5 covers the remaining canonical case. No running-app native drill was performed.
- Normal `UpdateService` construction compiles to Production trust and the fixed HTTPS GitHub manifest. Only a separately compiled `SPEEDMETER_UPDATE_LAB` branch exposes `ConfigureDevelopmentLab`, requires a sentinelled root, and restricts manifest/package traffic to one loopback origin (`UpdateService.cs:57–115,178–185,329–338`). The production path has no user-facing DevelopmentTest toggle. Lab packaging must remain visibly distinct from public release artifacts.
- App smoke/test-root mode routes settings, SQLite, crash reports, operational logs, and the instance lock into a validated disposable child (`App.xaml.cs:25–74`, `MainWindow.xaml.cs:55–66`, `SingleInstanceCoordinator.cs:90–97`). The lab build validates its own `<root>/install` location before configuring DevelopmentTest updater trust (`App.xaml.cs:45–64`). These are source guarantees; a live privacy/process isolation observation remains open.
