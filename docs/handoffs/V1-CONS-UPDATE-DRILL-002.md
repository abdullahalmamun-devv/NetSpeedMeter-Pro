## Code and contracts

- `UpdateService` now has an internal launch delegate for the Checks assembly. It captures the requested installer path and argument tokens while the same production method still performs final SHA-256 and real WinVerifyTrust publisher verification under a file handle that denies write/delete sharing. The normal public constructor still uses Production trust, the fixed GitHub Pages HTTPS manifest, and a real `Process.Start`.
- The launch request is `-Silent`, `-LaunchAfterInstall`, `-Dir`, `AppContext.BaseDirectory` via `ProcessStartInfo.ArgumentList`. The current installed app directory supplies the upgrade target; manifest and settings cannot change it. Installer specialist confirmed `-Dir <path>` support and is adding ownership-marker guards for custom locations.
- `#if SPEEDMETER_UPDATE_LAB` alone exposes `UpdateService.ConfigureDevelopmentLab(Uri manifestUri, string labRoot, string? databasePath)`. The caller must invoke it before constructing MainWindow/SettingsViewModel. It validates `TestSandboxGuard.ValidateRoot/ValidateChild`, derives `<labRoot>/update-staging`, and requires a loopback manifest origin. Under this symbol, the public constructor uses DevelopmentTest trust; without the symbol it remains Production-only. There is no consumer settings, environment, or CLI trust toggle.
- The lab manifest may use `http://127.0.0.1:<port>/updates/rc.json`. Its signed package URL must use the same scheme, host, and port with path `/abdullahalmamun-devv/NetSpeedMeter-Pro/releases/download/v<version>/SpeedMeterPro-<version>-Setup.exe`. Lab redirects must remain on the same origin. Release notes still require HTTPS. Normal builds retain HTTPS and GitHub Release URL restrictions.

## Non-destructive fixture coverage

- `ConsumerUpdateFixtures` uses an internal DevelopmentTest-only manifest signing seam and a signed local SpeedMeter PE to exercise manifest retrieval, streamed package download, SHA-256, **real** WinVerifyTrust and publisher verification, ready staging, final re-verification under the read lock, and capture of the exact launch arguments. The launch delegate records the request and never executes the PE. A second fixture modifies the staged file and confirms launch is blocked with Failed state. A loopback transport fixture accepts same-origin HTTP only in DevelopmentTest and rejects an off-origin response.
- The signed PE fixture selects an already test-signed RC.2/RC.1 `SpeedMeter.App.exe` from local release artifacts and skips if unavailable. This proves the verifier and launch boundary with a small executable stand-in; it does not prove the canonical Setup.exe upgrades or restarts the app.
- `SpeedMeter.Application` built successfully in Debug both with and without `SPEEDMETER_UPDATE_LAB`, each with zero warnings/errors. The lab build initially caught a compile-time URI scheme pattern error; it was fixed and both builds rerun successfully. A Checks-only compile succeeded before the newer installer test guard was concurrently edited. A later Checks build was blocked by transient errors in installer-owned `TestDeleteGuard.cs` and stale installer references; the installer specialist is resolving those. The new signed-PE fixtures were not run here, and no installer/uninstall or real user data was touched.
