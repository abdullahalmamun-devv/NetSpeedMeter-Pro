# V1-CONS-SAFETY-003 — Installer safety handoff

**Owner:** Windows Installer specialist  
**Reviewers:** Independent Security/Privacy, QA, Director  
**Authority:** PRD §§24, 25.1–25.2; AC-S03, AC-S07  
**Dependency:** Gate E1; RC.3 public baseline `b5f7ffe`  
**Gate:** Consumer safety closure remains open pending independent review and native packaged drill. Gate E2 is not authorized.

## Scope and design

- Removed the deferred `cmd.exe`/batch `rd /s /q` uninstall path and its CMD-specific path character rejection.
- An installed `Uninstall.exe` copies its exact bytes to a unique `%TEMP%\SpeedMeterPro.Cleanup\<nonce>` directory, verifies SHA-256 equality, and starts the copy in private `-CleanupExecutor` mode. The parent and helper prove each other's live process IDs through a current-user named pipe; the helper also checks the parent's process start time and waits for termination.
- The helper request is size-bounded and binds target path, original executable, SHA-256, parent PID/start time, nonce, and original command line. It is accepted only from the expected product temp location and a marked product installation. Validation runs again after the parent exits, just before uninstall mutation. The engine checks the marker again immediately before moving application files.
- Unmarked legacy canonical directories are now refused by uninstall validation; this avoids deleting a merely lookalike directory and requires a separate repair path if such an old installation is encountered.
- The copied Setup runs the normal GUI or silent uninstaller outside the installation. Its durable, target-hash-keyed result records `Pending`, then `ProductRemoved` after product deletion. A separate cleanup component changes that result to `Completed` only after deleting the copied Setup, or to `Failed` if final cleanup fails. A packaged drill must wait for final `Completed`, `janitor-result-<nonce>.txt` `Completed`, target absence, no quarantine sibling, and nonce-directory absence.
- Closing the initial GUI is exit code 1602 (canceled), so the helper result cannot claim `Completed` for a canceled uninstall.
- If the janitor cannot start or authenticate, the copied Setup records final `Failed`, returns exit code 1 after product removal, and shows an interactive warning. If the janitor fails after the copied Setup exits, it records final `Failed` and shows the warning itself. The original installed process exit code only confirms handoff, so callers must use the final result records.
- Purge and program deletion use same-parent quarantine moves followed by checked, non-recursive traversal. Every traversed item is checked for reparse attributes and containment. A failed purge still removes the app but reports that some local data could not be deleted. A failed binary cleanup reports an incomplete uninstall.
- A dedicated, signed, self-contained `SpeedMeterPro.TempCleanup.exe` is embedded in the installer. The installed uninstaller extracts it to one fixed `%TEMP%\SpeedMeterPro.Cleanup` path and verifies its SHA-256 against the embedded bytes. After product deletion, the copied Setup writes a create-new, nonce-bound request and starts this small component. They verify live process IDs through a current-user named pipe; the component checks the copied Setup's start time and image path, waits for exit, revalidates the executable hash and each path before deletion, then removes `Uninstall.exe`, `janitor.req`, and the empty nonce directory. A later uninstall prunes only stale, GUID-named, non-running nonce directories with expected files and no reparse points. The bounded `cleanup.log` records handoff failures.
- Main result files are keyed by target-path SHA-256 (one per target) and contain only `TargetHash`, `Nonce`, `State`, `Message`, and `Timestamp`, avoiding a persistent profile path. The nonce-keyed janitor result is a two-line text file beginning with `Pending`, `Completed`, or `Failed`. Both result types are pruned after 30 days on a later uninstall if names match exact product patterns and files are not reparse points. They can remain in `%TEMP%` until that cleanup or normal Windows temp maintenance. The fixed janitor executable is retained for reuse and is currently 11,184,897 bytes in the unsigned trimmed win-x64 publish; signing will change its exact size.

## Remaining evidence and limits

- The QA and Director runs exercised positive sentinelled purge and rejected stale-parent requests. All three new janitor checks passed: invalid request/parent/hash rejection, reparse insertion rejection, and sentinelled verified deletion preserving an unrelated sibling. This exercises the production validation and deletion functions but not the process/pipe handoff; the packaged native drill must cover that path.
- Release Engineering must run a packaged, sentinelled native uninstall and wait for both final result records, target and nonce-directory absence, and complete quarantine removal. Parent process exit code and `ProductRemoved` alone are insufficient evidence.
- Independent Security/Privacy review must decide acceptance; the Director alone can declare consumer closure.
- Checked managed traversal narrows but cannot eliminate a malicious same-user mutation race without handle-relative Windows APIs. If a reparse substitution is detected, cleanup stops and can leave a named quarantine directory. This is reported as incomplete.
- Package/test cleanup scripts still contain recursive filesystem deletion outside the production installer engine; their sentinel and path guards need continued review against same-user mutation during native drills.
- Windows build 19045 denied both direct self-delete and MoveFileEx delete-on-reboot for the previous 217 MB copied Setup. The dedicated janitor avoids relying on those mechanisms. Its own approximately 11 MB fixed signed executable remains in Temp for reuse; it is not a growing copy per uninstall. If janitor launch or deletion fails, final result is `Failed` and the copied Setup can remain until guarded stale-directory pruning on a later uninstall. A same-user attacker can still race path mutation between managed checks and file operations, which is why the native packaged drill and independent review remain required.
